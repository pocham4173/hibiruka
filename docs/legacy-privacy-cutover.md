# 旧共有領域を本人だけに限定する切り替え

個人の番号、UID、記録内容や本番の集計結果はこの文書に記載しない。
このコードの存在だけでは本番反映の完了を示さない。完了は切り替えワークフローの検証結果で判断する。

## 変更の目的と範囲

確認した本人が既存の予定・写真・買い物・ペット記録を開ける状態を保ち、別のアカウントによる閲覧・変更を止める。
保存先・文書IDを変えず、既存記録やLINEの送信先・予約・台帳をコピー、削除、編集しない。
LINEの送信先に登録されていることと、アプリ内の記録を閲覧できることは別の権限として扱う。

問い合わせ番号は所有権を取得するための秘密ではない。本人からの確認と作業許可を受けた管理作業にのみ使う。
明示的に許可された暗号文を既存の管理認証で復号し、既存候補に一意に一致したアカウントを選ぶ。
番号、UID、候補リスト、記録内容、認証トークンを公開ログに出さない。不一致・複数一致・有効期限切れでは停止する。

## 権限の変更

- Firestoreの旧 `isOwner()` は管理者専用の `config/legacyPrivacy` に指定された本人のみを許可する。
- 旧PINでの再参加と、クライアントによる `members` / `config/owners` の書き換えを閉じる。
- LINE Workerも旧領域への操作・再接続のたびに同じ管理設定を確認する。古いLINE連携や旧登録だけでは許可しない。
- 通信失敗時はアクセスを許可しない。他の個人別保存ルールと記録スキーマは変更しない。
- 画面は本人一致・version 1・activated trueの確認後だけ非公開の説明に変え、旧PIN変更案内を隠す。

## 当時の実行順序と停止条件

削除済みの `privacy-cutover.yml` は、ワークフロー自体がmainへ入る変更でのみ起動する設計だった。
通常の画面変更では再実行しない。ルールを扱う既存ワークフローと同じ同時実行グループを使う。

1. 同じコミットのLINE Workerが反映され、有効な定期実行を2回確認する。既存の送信予約だけを通常運用する。
2. 本人・旧設定の版・会員登録の状態・最新ルールを読み取り専用で確認する。既存の本人アカウントが存在しなければ停止する。
3. 最新の本番ルールの修正案を一時領域に作り、架空のアカウントで本人の許可、別人の拒否、自己昇格と再参加の拒否を検査する。
   不明な重複許可、既存の切り替え設定、テスト不合格では停止する。
4. 適用直前に状態を再確認し、既存記録のIDと更新時刻だけを控える。記録本文は読み取らない。
5. 管理設定と元ルールを同一プロジェクトの管理者専用 `config/legacyPrivacyBackup` に保全する。
   本人限定の管理設定を作り、ルールを反映する。旧設定・保全先・既存ロックが予想と違えば上書きしない。
6. 本人の実際の認証と一時テストアカウントから集計クエリを行い、本人は許可、他人は拒否になることを確認する。
   保全先は両者とも拒否されることを確認する。結果の本文は表示しない。
7. 元の記録IDと更新時刻が維持されていることを確認した後だけ旧ownersを本人に限定し、activatedを有効にする。
   一時テストアカウントは成功・失敗のどちらでも削除する。LINEのテスト送信は行わない。

## 失敗時

安全確認が済まなければactivatedを有効にせず、共有を広げる旧ルールへの自動巻き戻しもしない。
適用途中で停止した場合は管理設定・稼働中ルール・Workerを内部で確認してから復旧する。
既存ロックを削除して再実行する運用にはしない。保全した設定の検証・復元は管理者限定で行う。
既存記録への通常の書き込みと検証が重なった場合も、更新時刻の相違を検出して確認を止める。

## 確認の限界

エミュレーターでは本人の読み書きと他人の読み書き拒否を検査する。
本番の確認は既存記録を書き換えず、認証した集計クエリとID・更新時刻の比較で行う。
iPhone実機での表示・再起動・LINEアプリからの操作は、この自動検証とは別に確認が必要。
